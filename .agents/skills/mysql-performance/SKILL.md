Codex may use commands such as:

```bash
mysqldumpslow -s at -t 20 /var/log/mysql/mysql-slow.log
mysqldumpslow -s ar -t 20 /var/log/mysql/mysql-slow.log
```

Codex may also query the local MySQL server using:


Use read-only diagnostic queries by default.

Useful diagnostics include:

```sql
SHOW INDEX FROM articles;
SHOW INDEX FROM article_interactions;
SHOW INDEX FROM tags;
SHOW INDEX FROM events;
SHOW INDEX FROM feeds;
```

and Performance Schema queries such as:

```sql
SELECT
    COUNT_STAR AS executions,
    ROUND(SUM_TIMER_WAIT / 1000000000000, 2) AS total_seconds,
    ROUND(AVG_TIMER_WAIT / 1000000000, 2) AS avg_ms,
    SUM_ROWS_EXAMINED AS rows_examined,
    SUM_ROWS_SENT AS rows_sent,
    SUM_NO_INDEX_USED AS no_index,
    SUM_NO_GOOD_INDEX_USED AS no_good_index,
    QUERY_SAMPLE_TEXT
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'rssmonster'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

Codex may use appropriate `sys` schema views as well.

## Workflow

When investigating a performance problem:

1. Find the application code producing the query.
2. Determine whether it comes from Sequelize or raw SQL.
3. Inspect the slow-query log and Performance Schema where useful.
4. Inspect the existing relevant indexes.
5. Obtain the actual generated SQL where needed.
6. Use `EXPLAIN ANALYZE` for important SELECT queries when safe.
7. Identify why the query is expensive.
8. Only then propose a query change or index.

Do not infer that a query is efficient merely because `no_index = 0`.

Pay particular attention to:

* rows examined versus rows returned;
* actual execution time;
* index choice;
* index range size;
* filesort;
* temporary tables;
* nested-loop cardinality;
* correlated subqueries;
* `EXISTS`;
* `IN`;
* large joins;
* `GROUP BY`;
* `ORDER BY`;
* expressions around indexed columns;
* functions such as `LOWER()`, `CASE`, `COALESCE`, `GREATEST`, `MONTH()` and `DAYOFMONTH()` that can prevent efficient index access.

## Sequelize rules

RSSMonster primarily uses Sequelize.

Always locate the source code responsible for the SQL before changing it.

If the query is generated by Sequelize:

* improve the Sequelize implementation;
* do not replace it with raw SQL merely for optimization;
* preserve parameterization;
* preserve behavior and API contracts.

If the existing implementation already uses raw SQL:

* optimize that SQL directly when appropriate;
* preserve parameterized values;
* never concatenate user input into SQL.

When an index is needed:

* implement it through the project's Sequelize migration mechanism;
* follow existing migration conventions;
* use descriptive index names;
* make migrations reversible;
* inspect existing indexes first;
* do not introduce redundant indexes.

Remember that additional indexes increase:

* INSERT cost;
* UPDATE cost;
* storage;
* buffer-pool pressure.

Therefore do not add speculative indexes.

## EXPLAIN ANALYZE safety

`EXPLAIN ANALYZE` actually executes the query.

Use it freely for safe SELECT statements on the local development database.

Do not use it for destructive statements or anything with side effects.

When comparing an optimization, capture:

```text
Before:
- execution time
- rows examined / actual rows
- selected index
- sort/temp-table behavior

After:
- execution time
- rows examined / actual rows
- selected index
- sort/temp-table behavior
```

## Important known RSSMonster observations

Recent profiling showed several behavioral Article queries that calculate timestamps dynamically using expressions involving:

```text
CASE
COALESCE
GREATEST
MONTH()
DAYOFMONTH()
lastClickedAt
favoritedAt
positiveFeedbackAt
negativeFeedbackAt
lastMeaningfulReadAt
publishedAt
```

Do not assume another normal B-tree index will solve these queries. Investigate whether the query shape or stored data model should be improved.

Another known expensive pattern is:

```sql
LOWER(title) LIKE '%term%'
```

The Article table already has a FULLTEXT index on:

```text
(title, contentText)
```

If investigating this query, first understand whether arbitrary substring matching is required before changing it to FULLTEXT search.
